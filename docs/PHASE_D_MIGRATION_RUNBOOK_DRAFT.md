# Phase D production data migration rehearsal — DRAFT, NOT EXECUTED

This runbook does not authorize a source dump, production restore, environment change or deployment. Phase C only created empty local PostgreSQL infrastructure. A rehearsal must precede a separately approved single-writer cutover. Delta remains excluded.

1. **Freeze and identify writers.** Verify crawler/digest/health cron remains paused, no running CLI/retry/delta/WeChat jobs, and identify Vercel/ECS subscription writers. A real cutover also needs a controlled web write freeze or reliable snapshot-plus-delta strategy. Record exact application releases and protected configuration hashes. Do not infer a complete freeze from cron alone.
2. **Resolve email uncertainty.** Inspect pending deliveries, provider IDs, accepted timestamps and running digest runs via an authorized, secret-safe source audit. Reconcile provider acceptance before retry decisions. No blind pending reset or resend. Record provider idempotency retention limits and a handling plan for ambiguous results.
3. **Approve source export.** Obtain dedicated source access and use explicit public-table allowlist: notices, subscriptions, subscription_sources, email_deliveries, digest_runs, crawl_runs, resend_webhook_events. Rehearsal should use a consistent snapshot with a documented capture time. Do not export auth/storage/vault/platform objects, roles, ownership or broad grants. Check source/client PostgreSQL version compatibility; protect archive and checksum with root-only permissions.
4. **Restore into a NEW rehearsal database first.** Use the Phase B canonical baseline, explicit column mapping/data-only import and dependency-aware ordering. Preserve UUIDs, all timestamps including microseconds, JSONB/NULL distinctions, tokens, provider IDs, idempotency keys, statuses and metadata. Do not replay historical backfill migrations or regenerate identifiers. Keep standard public schema when testing full custom-format archive restore. Do not destructively rehearse in the empty production target.
5. **Integrity gates.** Compare all seven row counts and per-table stable row hashes; check columns/defaults/nullability, 29 indexes, all constraints/FKs, 3 enabled triggers and function ownership. Verify zero orphans, token/key uniqueness and exact field parity without printing those values. Inventory sub-millisecond delivery window endpoints: current JS Date retry interfaces cannot represent them exactly, so explicitly resolve any identity mismatch before cutover. Validate accepted/sent/delivered/failed and running/success distributions, half-open Beijing/UTC windows, source counts, repository reads and mock-only sends.
6. **Readiness gates before cutover.** Configure private encrypted offsite backups and test recovery on a separate host; verify disk/memory/connection budgets and maintenance access. Validate signed Vercel→ECS connectivity. Establish monitoring, rollback deadline, source retention, on-call owner and exact immutable application commit. Real data restore compatibility has not yet been verified.
7. **Application cutover — separate authorization.** Confirm all writers frozen; take final source snapshot/delta; validate target; back up target. Introduce protected runtime credentials to a new approved ECS release only then. Deploy the matching canonical Vercel proxy under a controlled plan. Confirm reads and explicitly approved synthetic mutations with mail mocked before enabling a single scheduled writer. Do not enable delta.
8. **Rollback.** Before any new target writes, rollback can restore prior app configuration/releases while keeping source intact. After new PostgreSQL writes, a backend flip alone loses data: freeze both sides, reconcile/export new target changes and email acceptance, restore a verified consistent state, then select one writer. Never allow simultaneous independent Supabase/PostgreSQL writers. Test the rollback procedure and retain source/archive until its acceptance window ends.
